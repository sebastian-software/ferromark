## Document sizes

The main cases use 2, 5, and 10 KiB of synthetic CommonMark with headings,
emphasis, links, lists, quotes, and fenced code. These are controlled examples,
not an estimate of the typical document distribution. Tiny inputs diagnose
per-call overhead; 50 KiB and 1 MiB belong in the detailed long-document and
stress results. Time per document is often more useful for an application than
throughput alone.

## Feature sets

Time per complete document, in microseconds; lower is faster. Compare parsers
within a row. Syntax density, input size, and output expansion differ between
rows, so these are workload measurements rather than additive feature prices.

## What the comparison guarantees

Every displayed input/configuration pair passes an output-equivalence gate
across all five parsers before timing. The limited comparator allows documented
serialization differences, including entity spelling, attribute order, and
void-element slashes. Ordinary HTML flow whitespace is normalized while retaining
inline word separators and literal text; arbitrary CSS whitespace rules are
outside this check. It preserves visible text, URL values, code whitespace,
classes, IDs, and checkbox attributes. This is a corpus check, not proof that
the parsers agree on arbitrary Markdown.

Each displayed result is the median of three run medians, with alternating
parser order. Each run uses 80 windows totaling at least five seconds of
sampling per parser/input after three seconds of warmup. Options are constructed
outside the timer; fresh parser setup, parsing, owned output, and destruction
are inside it. The [full report](https://github.com/sebastian-software/ferromark/blob/main/docs/reports/2026-09-11-benchmark-refresh.md)
records run variation, output sizes, mismatches, exact options, and source hashes.

This page and the [repository README](https://github.com/sebastian-software/ferromark#benchmarks)
are generated from the same raw measurements and checked at build time.
Historical stable-toolchain/System-allocator results and the
[September 5 Bun experiment](https://github.com/sebastian-software/ferromark/blob/main/docs/reports/2026-09-05-bun-comparison.md)
retain their original conditions; their figures are not mixed into these tables.

## Native Bun and reproduction

The [five-parser harness](https://github.com/sebastian-software/ferromark/blob/main/benchmarks/bun-comparison/README.md)
builds Bun's native Markdown parser without JavaScript. Its
[provenance](https://github.com/sebastian-software/ferromark/blob/main/benchmarks/bun-comparison/PROVENANCE.md)
traces md4c through Zig and Rust ports. Bun retains C++ Highway searches and C
mimalloc. The harness also binds C-md4c's allocation calls to the same mimalloc;
this is a controlled benchmark environment, not the normal library build.

Follow the harness README to prepare the pinned Bun checkout and native build
support. Then use the measured lockfile and a pinned md4c checkout:

```bash
git clone https://github.com/mity/md4c.git ../md4c
git -C ../md4c checkout --detach 65c6c9d
python3 benchmarks/bun-comparison/prepare.py "$BUN_BENCH_DIR" "$BUN_BENCH_WORK" \
  --md4c ../md4c \
  --lockfile docs/reports/2026-09-11-benchmark-refresh/native/Cargo.lock
python3 benchmarks/bun-comparison/run.py "$BUN_BENCH_DIR" /private/tmp/new-benchmark-run
```

Ordinary library builds, tests, and package installs do not build Bun or md4c.

## Feature and lifecycle costs

`cargo bench --bench options` keeps its document constant while changing
presets and individual flags. That mixes syntax actually used with enabled
but unused detection paths. The [feature study](https://github.com/sebastian-software/ferromark/blob/main/docs/reports/2026-09-11-benchmark-refresh.md#feature-and-lifecycle-costs)
replays 140 scenarios and 292 input/configuration pairs to separate these questions:

| Measurement | Interpretation |
| --- | --- |
| Option off/on without matching syntax | Identical HTML isolates detection and setup costs. |
| Option off/on with matching syntax | Changed HTML includes additional parsing and rendering work. |
| Fresh output versus retained Renderer | Measures the value of keeping parser state and buffers between calls. |
| Different core Markdown constructs | Compares workloads with different structures and output sizes. |

Allocation counters run separately from uninstrumented timings; cumulatively
requested bytes are not peak memory. The
[earlier feature study](https://github.com/sebastian-software/ferromark/blob/main/docs/reports/2026-09-10-markdown-feature-costs-final.md)
found most unused options inexpensive, with literal-autolink detection a
measurable exception. Its [GFM CPU profiles](https://github.com/sebastian-software/ferromark/blob/main/docs/reports/2026-09-10-gfm-profiling.md)
and [optimization decisions](https://github.com/sebastian-software/ferromark/blob/main/docs/reports/2026-09-10-markdown-feature-optimizations.md)
explain the hypotheses behind the rerun. Choose options for semantics and
measure the actual application workload.

## Other comparison surfaces

The [two-parser harness](https://github.com/sebastian-software/ferromark/blob/main/benchmarks/pulldown-comparison/README.md)
covers CommonMark, shared GFM, and extended syntax intersections including
footnotes, math, superscript, and callouts. Its semantic spot checks do not
establish equivalent output for every timed fixture. Its stable compiler and
lifecycle diagnostics remain separate from the five-parser publication tables.

A matched untrusted-input pipeline and native x86 measurements remain open in
the [comparison plan](https://github.com/sebastian-software/ferromark/blob/main/docs/plans/2026-09-11-benchmark-comparability-and-documentation.md).
Ferromark's secure-default output should not be ranked against an unchecked
HTML passthrough operation as if both performed the same task.

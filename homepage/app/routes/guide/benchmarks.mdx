## Workflow benchmarks

What does the Markdown step cost in an application? These workloads measure
complete sets of documents, including output allocation and release. Time and
exact Rust heap measurements come from separate runs so allocation tracking does not affect timings.

### Preview user-authored comments

Twelve authored examples. Ferromark uses secure defaults; pulldown-cmark and Comrak use application adapters for matching HTML escaping, URL checks, heading IDs, and callouts. Each returns owned HTML that is released immediately. The retained `Renderer` is Ferromark's scratch-reuse variant.

12 documents · 2,081 input bytes · 2,901 HTML bytes (Ferromark).

| API / output lifetime | Time / complete workload | Peak live heap¹ | Allocated per workload² |
| --- | ---: | ---: | ---: |
| Ferromark · Fresh `to_html` calls | 11.7 µs | 6.9 KiB | 47.2 KiB |
| Ferromark · Retained `Renderer` | 7.3 µs | 8.4 KiB | 5.6 KiB |
| pulldown-cmark + preview adapter | 15.1 µs | 17.2 KiB | 202.5 KiB |
| Comrak + preview adapter | 38.8 µs | 7.9 KiB | 115.4 KiB |

### Render documentation with metadata

Three actual guide pages, rendered under the same untrusted policy. Ferromark `parse` and the two application adapters return HTML, raw front matter, and headings with matching navigation IDs; each complete result is released.

3 documents · 6,763 input bytes · 8,725 HTML bytes (Ferromark).

| API / output lifetime | Time / complete workload | Peak live heap¹ | Allocated per workload² |
| --- | ---: | ---: | ---: |
| Ferromark · `parse`: HTML + front matter + headings | 20.3 µs | 20.6 KiB | 57.2 KiB |
| pulldown-cmark + metadata adapter | 31.1 µs | 44.2 KiB | 118.0 KiB |
| Comrak + metadata adapter | 80.4 µs | 71.6 KiB | 223.2 KiB |

Reusing `Renderer` reduced time and allocation traffic for these previews.
Its peak heap was higher: retained scratch remains part of the worker's memory budget.

For the documentation collection, compare each engine's two output lifetimes
before using a memory figure to size your pipeline. Keeping completed HTML
in memory is application work included in the retained-output rows.

The metadata rows measure complete HTML-and-metadata operations; they do
not isolate the incremental cost of collecting headings or represent an
end-to-end site build.

Preview and metadata comparisons include the application adapters needed
by pulldown-cmark and Comrak. Their escaping, URL checks, heading IDs,
and metadata collection are timed and counted in heap usage. These are
complete integration costs, not rankings of body-only parser calls.

¹ Peak simultaneously live **requested heap**, including retained parser scratch
and the chosen HTML output lifetime. Loaded inputs, stack, allocator overhead,
and cached pages are excluded; this is **not process RAM/RSS**. ² Cumulative
allocation traffic, not simultaneously required memory.

Apple M1 Pro, macOS 26.6.2, Rust 1.97.1, generic CPU target, system allocator.
Three process rounds per variant; median of round medians. Native, warmed,
single-threaded API work only: no Node.js bindings, I/O, templates, or syntax
highlighting. These project snapshots and authored comments are examples, not
a production-traffic distribution or a complete site build. No x86-64 run is included.

**Process RSS is a different memory measurement from the Rust heap table.**
It includes the runtime/JIT, stacks, input, allocator/GC reserves, and worker
infrastructure. Each cell is the median of three whole-process peaks during
startup, warmup, repeated collection work, and shutdown. It is not incremental
parser memory, a single-request peak, or a concurrent-service capacity estimate.

Timing still surrounds only completed Markdown work. GC in those windows is
included; OS peak-RSS accounting needs no instrumented allocator. Collection
timings and the earlier Rust heap measurements are separate fresh runs.

Ox Content's extra generated heading IDs may be admitted as additional output;
content, heading levels, links, tables, and checkbox states must remain intact.
cmark's core-only dialect cannot complete the GFM collection. No input is
removed to obtain a timing row. Full secure-preview and metadata adapters are
currently measured for Ferromark, pulldown-cmark, and Comrak only; the wider
HTML-only collection comparison does not establish those additional contracts.

## What the comparison guarantees

Every input/configuration pair in the five-parser tables above passes a workload
review across those five parsers. HTML equality is not required: known renderer differences and small
bugs are disclosed. The separate HTML comparator retains text, URL values,
code whitespace, classes, and checkbox states so output fidelity stays inspectable.
No normalization is included in the timed parser calls.

Each displayed result is the median of three run medians, with alternating
parser order. Each run uses 80 windows totaling at least five seconds of
sampling per parser/input after three seconds of warmup. Options are constructed
outside the timer; fresh parser setup, parsing, owned output, and destruction
are inside it. The [full report](https://github.com/sebastian-software/ferromark/blob/main/docs/reports/2026-09-12-ox-corpus-optimizations/REPORT.md)
records run variation, output sizes, mismatches, exact options, and source hashes.

The five-parser tables on this page and in the [repository README](https://github.com/sebastian-software/ferromark#benchmarks)
are generated from the same raw measurements and checked at build time.
Historical stable-toolchain/System-allocator results and the
[September 5 Bun experiment](https://github.com/sebastian-software/ferromark/blob/main/docs/reports/2026-09-05-bun-comparison.md)
retain their original conditions; their figures are not mixed into these tables.

## Native Bun and reproduction

The [five-parser harness](https://github.com/sebastian-software/ferromark/blob/main/benchmarks/bun-comparison/README.md)
builds Bun's native Markdown parser without JavaScript. Its
[provenance](https://github.com/sebastian-software/ferromark/blob/main/benchmarks/bun-comparison/PROVENANCE.md)
traces md4c through Zig and Rust ports. Bun retains C++ Highway searches and C
mimalloc. The harness also binds C-md4c's allocation calls to the same mimalloc;
this is a controlled benchmark environment, not the normal library build.

Follow the harness README to prepare the pinned Bun checkout and native build
support. Then use the measured lockfile and a pinned md4c checkout:

```bash
git clone https://github.com/mity/md4c.git ../md4c
git -C ../md4c checkout --detach 65c6c9d
python3 benchmarks/bun-comparison/prepare.py "$BUN_BENCH_DIR" "$BUN_BENCH_WORK" \
  --md4c ../md4c \
  --lockfile docs/reports/2026-09-12-ox-corpus-optimizations/bun/Cargo.lock
python3 benchmarks/bun-comparison/run.py "$BUN_BENCH_DIR" /private/tmp/new-benchmark-run
```

Ordinary library builds, tests, and package installs do not build Bun or md4c.

## Feature and lifecycle costs

`cargo bench --bench options` keeps its document constant while changing
presets and individual flags. That mixes syntax actually used with enabled
but unused detection paths. The [feature study](https://github.com/sebastian-software/ferromark/blob/main/docs/reports/2026-09-11-benchmark-refresh.md#feature-and-lifecycle-costs)
replays 140 scenarios and 292 input/configuration pairs to separate these questions:

| Measurement                           | Interpretation                                                        |
| ------------------------------------- | --------------------------------------------------------------------- |
| Option off/on without matching syntax | Identical HTML isolates detection and setup costs.                    |
| Option off/on with matching syntax    | Changed HTML includes additional parsing and rendering work.          |
| Fresh output versus retained Renderer | Measures the value of keeping parser state and buffers between calls. |
| Different core Markdown constructs    | Compares workloads with different structures and output sizes.        |

Allocation counters run separately from uninstrumented timings; cumulatively
requested bytes are not peak memory. The
[earlier feature study](https://github.com/sebastian-software/ferromark/blob/main/docs/reports/2026-09-10-markdown-feature-costs-final.md)
found most unused options inexpensive, with literal-autolink detection a
measurable exception. Its [GFM CPU profiles](https://github.com/sebastian-software/ferromark/blob/main/docs/reports/2026-09-10-gfm-profiling.md)
and [optimization decisions](https://github.com/sebastian-software/ferromark/blob/main/docs/reports/2026-09-10-markdown-feature-optimizations.md)
explain the hypotheses behind the rerun. Choose options for semantics and
measure the actual application workload.

## Other comparison surfaces

The [two-parser harness](https://github.com/sebastian-software/ferromark/blob/main/benchmarks/pulldown-comparison/README.md)
covers CommonMark, shared GFM, and extended syntax intersections including
footnotes, math, superscript, and callouts. Its semantic spot checks do not
establish equivalent output for every timed fixture. Its stable compiler and
lifecycle diagnostics remain separate from the five-parser publication tables.

A matched untrusted-input pipeline and native x86 measurements remain open in
the [comparison plan](https://github.com/sebastian-software/ferromark/blob/main/docs/plans/2026-09-11-benchmark-comparability-and-documentation.md).
Ferromark's secure-default output should not be ranked against an unchecked
HTML passthrough operation as if both performed the same task.

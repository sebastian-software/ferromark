# Add Highlighting and Mermaid Diagrams

Highlight code with [Ferriki](https://github.com/sebastian-software/ferriki) and
turn Mermaid fences into static SVG with
[Ferrigura](https://github.com/sebastian-software/ferrigura). Both engines reach
Ferromark the same way. Your application installs and initializes them, then
hands them to the renderer. Markdown that needs neither engine pays nothing for
them.

## Choose an integration

| Runtime | Highlighting                                              | Mermaid diagrams                                            |
| ------- | --------------------------------------------------------- | ----------------------------------------------------------- |
| Rust    | `ferriki` feature with `FerrikiHighlightHooks`            | `ferrigura` feature with `FerriguraHooks`                   |
| Node.js | `@ferriki/core` through `createLineHighlighter`           | `@ferrigura/core` through `createDiagramCodeRenderer`       |
| Native  | `CodeCompiler` plugin `ferriki` in a custom plugin bundle | `CodeCompiler` plugin `ferrigura` in a custom plugin bundle |

Code hooks for Node.js arrive with Ferromark 4.0: `composeCodeHooks`,
`createLineHighlighter`, and `createDiagramCodeRenderer`. Ferromark 3.7 offers
whole-block HTML callbacks and `toHtmlWithHighlighter` only.

## How code hooks work

A code block passes through two stages, in Rust and in Node.js alike:

1. **Replace the whole block** with `render_code_block` in Rust or
   `renderCodeBlock` in Node.js. The engine returns complete markup, such as a
   diagram, and the block is replaced.
2. **Highlight its lines** with `highlight_code_block` or `highlightCodeBlock`.
   The engine returns one HTML fragment per line plus block colors; Ferromark
   keeps the wrapper, line annotations, title, and JSX component around them.

Whole-block replacements run first. When none handles a block, highlighting
runs; within each stage the first hook that returns a result wins. Every hook
receives the code, its language and metadata, and the block's original UTF-8
byte range, so errors can name a file and line. JSX output always applies fence
metadata such as `{1}` and `title="…"`; HTML output applies it when code
annotations are enabled.

## Highlight code and render diagrams in Node.js

```sh
npm install ferromark @ferriki/core @ferrigura/core
```

```js
import { Renderer } from "@ferrigura/core";
import { createHighlighter } from "@ferriki/core";
import {
  compileJsx,
  composeCodeHooks,
  createDiagramCodeRenderer,
  createLineHighlighter,
  toHtmlWithCodeRenderer,
} from "ferromark";
import { readFile } from "node:fs/promises";

const themes = {
  light: "github-light-default",
  dark: "github-dark-default",
};
const highlighter = await createHighlighter({
  themes: Object.values(themes),
  langs: ["ts"],
});

const diagrams = createDiagramCodeRenderer(new Renderer(), {
  colorScheme: "auto",
});
const highlightCodeBlock = createLineHighlighter(highlighter, { themes });
const hooks = composeCodeHooks(diagrams, { highlightCodeBlock });

const source = await readFile("guide.md", "utf8");
const html = toHtmlWithCodeRenderer(source, hooks);
const jsx = compileJsx(source, { codeBlockComponent: "CodeBlock" }, hooks);
```

The same hooks work with `transformWithCodeRenderer`, `CodeCompiler.compile`,
and prepared documents. JSX output converts the diagram's SVG to JSX, keeping
case-sensitive SVG attributes such as `markerWidth`. A theme pair writes
`--shiki-light` and `--shiki-dark` CSS variables, so your stylesheet decides
which colors apply.

## Load languages before rendering

Hooks run synchronously, while Ferriki loads grammars asynchronously. Prepare
the document first, load the languages it uses, then render:

```js
import { prepareDocument } from "ferromark";

const prepared = prepareDocument(source);
const { codeBlocks } = prepared.metadata;
const languages = new Set(codeBlocks.map((block) => block.language));
for (const language of languages) {
  if (language) await highlighter.loadLanguage(language).catch(() => {});
}
const jsx = prepared.render({}, hooks);
```

A language that is still missing falls back to plain code and reports through
`onHighlightError`.

## Handle failures

Both adapters keep ordinary code output when their engine fails and report the
failure with the block's byte range:

```js
const diagrams = createDiagramCodeRenderer(new Renderer(), {
  onRenderError(error, { start }) {
    console.warn(`Diagram at byte ${start} kept as code:`, error);
  },
});
const highlight = createLineHighlighter(highlighter, {
  themes,
  onHighlightError(error, { lang, start }) {
    console.warn(`Could not highlight ${lang} at byte ${start}:`, error);
  },
});
```

Hooks you write yourself can throw instead; the render call then throws too.
Results are checked synchronously, so a Promise or a value of the wrong shape is
an error.

## Use native plugins in a custom bundle

A custom build can compile the engines into the Ferromark addon, so no
JavaScript runs per code block. The
[Native plugin bundles workflow](https://github.com/sebastian-software/ferromark/blob/main/docs/plugin-bundles.md)
builds an installable tarball for `none`, `ferriki`, `ferrigura`, or `all`.
Install it in place of the registry package:

```sh
npm install /path/to/ferromark-custom-bundle.tgz
```

````js
import { availableCodePlugins, CodeCompiler } from "ferromark";

console.log(availableCodePlugins()); // ["ferrigura"] in a diagram bundle
const compiler = new CodeCompiler({
  plugins: [
    {
      name: "ferrigura",
      options: { colorScheme: "auto", idPrefix: "guide" },
    },
  ],
});
const source = "```mermaid\nflowchart LR\nA[Markdown] --> B[SVG]\n```";

console.log(compiler.toHtml(source)); // Inline SVG in the HTML
console.log(compiler.compile(source).body); // JSX for the same diagram
console.log(compiler.takeDiagnostics()); // [] for a valid diagram
````

The bundles are workflow artifacts with private versions, not registry
releases. The standard package reports `[]` from `availableCodePlugins()`.

## Mermaid output

Diagrams render to SVG in Rust, without a browser or Mermaid runtime. Automatic
light and dark styles live in the SVG's own CSS and need no JavaScript.

- **Stable IDs.** Each diagram's SVG namespace is a prefix plus the fence's
  byte offset, `fm-mermaid-<offset>` by default. Repeated, prepared, HTML, and
  JSX renders produce the same IDs. Give each document its own prefix when you
  combine several on one page.
- **Fallback.** Invalid or unsupported diagrams keep escaped code. The native
  plugin also records a diagnostic; `errorPolicy: "throw"` makes it strict.
- **Trust.** The native plugin checks every SVG against a static allow-list
  before emitting it: no scripts, event attributes, external resources, or
  `foreignObject`. Hook output is trusted application HTML and skips that check.

The [Mermaid guide](https://github.com/sebastian-software/ferromark/blob/main/docs/ferrigura.md)
covers options, the SVG policy, and the engine version. The
[code-block hook contract](https://github.com/sebastian-software/ferromark/blob/main/docs/code-block-renderers.md)
describes both stages in detail. For the shared output boundary, see
[rendering and trust](/guide/rendering).
